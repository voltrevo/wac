# 0275b — withdrawn: a `core/` edit needs `deno task gen:core`, and I did not run it

- **Status:** closed — agent-b, 2026-08-27: **not a bug.** `packages/wacc/src/coretext.wac` embeds
  `core/vec.wac`, so a *project* import reads the embedded copy and my edit to the file on disk had
  not reached it. Running `deno task gen:core` makes the same program compile
- **Fixed in:** nothing — the compiler was right throughout
- **Claimed by:** agent-b (2026-08-27)
- **Reported by:** agent-b
- **Date:** 2026-08-27
- **Kind:** bug
- **Symptom:** none — the compiler was reporting a method that genuinely did not exist

## What I thought I had

Adding `fold` to `core/vec.wac` and calling it, the same source compiled through a **path** import and
was refused through a **project** import:

```wac
import { Vec } from "core/vec.wac";     // no such method
import { Vec } from "…/core/vec.wac";   // compiles
```

## What it actually was

`coretext.wac` embeds `core/`'s files as string literals — `if (path == "core/vec.wac")` returns the
embedded text — so a project import resolves to the copy **inside the compiler**, not to the file on
disk. My `fold` was on disk only. A path import reads the disk, which is exactly why the two
disagreed.

`deno task gen:core` regenerates both embeddings, and after it the project import compiles and runs.
The file that named the task was in front of me the whole time: `coretext.wac`'s first line is
*"Generated by `deno task gen:core` … Do not edit."*

## What it cost, which is the reason this is written up rather than deleted

**I changed the compiler to make a correct diagnostic go away.** Believing the refusal was wrong, I
widened `checkMethodCall`'s generic-receiver arm so an instantiation would take it — and that arm
returns silently when it cannot find the method, so `a.nosuchmethod()` on any `Vec<i32>` stopped being
reported at all. The suite stayed green, because nothing in it calls a method that does not exist.
Reverted; the diagnostic is back and checked.

That is the shape worth remembering: a refusal you believe is a false alarm may be resting on
something true, and "fix" it and you delete a real check. What I should have asked first is not *why
is the checker wrong* but *is the thing it says missing actually there* — in the file the compiler
reads, not the one I edited.

## The trap, stated plainly for whoever meets it next

**Editing any file under `core/` has no effect on a project import until `deno task gen:core` runs.**
The path import keeps working, so the two spellings disagree and it reads exactly like an
import-resolution bug in the compiler. `CLAUDE.md` documents `gen:core`; what it does not say is what
the failure looks like when you forget it.
